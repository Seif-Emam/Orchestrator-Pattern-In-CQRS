Checkout Workflow Architecture Migration

From Direct Command Chaining to the Orchestrator Pattern

تقرير معماري شامل يوضح تفاصيل نقل وتطوير الـ Order Checkout Workflow في نظام الـ E-Commerce من Monolithic Command Handler بيعمل Direct Command Chaining وبيشيل كل الـ responsibilities، لـ Orchestrator-based Architecture بتعتمد على Focused Steps مع Explicit Reverse Compensation وإدارة واضحة للـ Workflow State.

Section 02 // Overview

Executive Summary

ملخص تنفيذي يوضح الدوافع المعمارية للـ Migration، ما تم تغييره، وما تم الحفاظ عليه بدقة.

Scope & Architectural Objective

Zero-Regression Migration

الـ Checkout Workflow بيمثل Business Transaction معقدة بتمر بـ 5 خطوات متتالية عبر Bounded Contexts مختلفة: Order Validation، Inventory Reservation، Payment Processing، Shipment Creation، و Order Confirmation.

قاعدة أساسية في الـ Migration: الـ Migration غيرت الـ Architecture Organization والـ Workflow Coordination، لكن حافظت بنسبة 100% على الـ existing API contracts، الـ Domain Entities، الـ Database Persistence، الـ Standardized JSON Responses، والـ Centralized Error Handling بدون أي Regression في الـ Business Behavior.

Before Problem
Handler كان شايل كل الـ steps والـ rollback المعقد يدويًا.
After Solution
Orchestrator مخصص بينسق الـ Steps وينفذ Reverse Compensation.
Handler Impact
تحول لـ Thin Delegator مكون من 15 سطر فقط.

Section 05 // Root Cause Analysis

Why The Old Design Became a Problem

تحليل معماري للمشاكل والعيوب التصميمية التي أدت لضرورة الترحيل إلى الـ Orchestrator Pattern.

01. Monolithic Handler

تضخم حجم ومسؤوليات الـ Handler

الـ CheckoutCommandHandler كان بيجمع Validation + Inventory + Payment + Shipment + Finalization + Compensation في ملف واحد تجاوز 180 سطرًا، مما جعله God Handler عرضة للأخطاء عند أي تعديل.

02. Single Responsibility Violation

كسر مبدأ المسؤولية الواحدة (SRP)

الـ Handler كان عنده أسباب متعددة للتغيير: لو طريقة الـ Validation اتغيرت، أو الـ Payment Gateway اتغيرت، أو خطوات الـ Shipping اتغيرت، كل ده كان بيجبرنا نعدل في نفس الـ Handler.

03. Fragile Manual Compensation

هشاشة الـ Rollback اليدوي (Spaghetti Logic)

عملية معالجة الفشل كانت معتمدة على شروط متداخلة داخل الـ catch block زي if (inventoryReserved) و if (paymentProcessed)، وده بيخلي التعويض معرض لنسيان خطوات أو حدوث State Inconsistency.

04. Tight Temporal Coupling

الارتباط الوثيق وصعوبة التوسع (OCP Violation)

لو البيزنس طلب إضافة خطوة جديدة في الـ Checkout (زي Fraud Check أو Loyalty Points أو Email Notification)، كان لازم نفتح الـ Handler ونحشر الخطوة والـ Rollback بتاعها جواه.

05. Combinatorial Testing Pain

تعقيد الـ Unit Testing والـ Mocking

عشان تعمل Unit Test لسيناريو واحد في الـ Checkout، كنت محتاج تعمل Mocking لكل MediatR Command ولكل حالة نجاح وفشل وتتأكد من شروط الـ rollback في test fixture واحد ضخم.

Section 07 // Pipeline Anatomy

Workflow Steps Detailed Breakdown

شرح تفصيلي لكل Step في الـ Pipeline ومسؤوليتها المفردة وكيفية تنفيذ الـ Compensation الخاص بها.

Step 01

OrderValidationStep (`IOrderValidationStep`)

Validation Phase

بتتحقق من وجود الـ Order في الـ Database، وتتأكد إن حالته OrderStatus.Pending، وإن قائمة الـ Items مش فاضية ومطابقة للشروط. لو الـ Order غير موجود أو في حالة تانية، بتوقف الـ Workflow فورًا وترمي NotFoundException أو DomainException بدون لمس أي Bounded Context تاني.

Execution: Task<Order> ExecuteAsync(Guid orderId, CancellationToken cancellationToken)
Step 02

InventoryReservationStep (`IInventoryReservationStep`)

Compensable Step

مسؤولة عن إرسال ReserveInventoryCommand للـ Inventory Domain عشان تحجز وتنقص كميات المنتجات المطلوبة من الـ Stock. وفي حالة حدوث أي فشل لاحق في الـ Workflow، بتقدم ميثود CompensateAsync عشان ترجع الـ Stock المحجوز فورًا لحالته الأصلية.

Compensation: Task CompensateAsync(Order order, ReserveInventoryResponse reservation, CancellationToken ct)
Step 03

PaymentProcessingStep (`IPaymentProcessingStep`)

Compensable Step

مسؤولة عن تنفيذ عملية الدفع عبر الـ Payment Gateway وتوليد TransactionId وتسجيل الـ PaymentStatus.Paid. ولو الـ Shipment فشل بعد نجاح الدفع، بتقدم ميثود CompensateAsync بتعمل Refund للمبلغ وتسجل الـ PaymentStatus.Refunded.

Compensation: Task CompensateAsync(Order order, ProcessPaymentResponse payment, CancellationToken ct)
Step 04

ShipmentCreationStep (`IShipmentCreationStep`)

Logistics Phase

بتتواصل مع شركة الشحن (Carrier) وتتأكد من صحة العنوان وبتصدر TrackingNumber رسمي وتربط الـ Shipment بالـ Order.

Execution: Task<CreateShipmentResponse> ExecuteAsync(Order order, string address, string carrier, CancellationToken ct)
Step 05

FinalizeCheckoutStep (`IFinalizeCheckoutStep`)

Completion Phase

بتحدث حالة الـ Order في الـ Database لـ OrderStatus.Confirmed وتسجل الـ UpdatedAt timestamp وتجمع كل النتائج من الـ Context وتبني الـ CheckoutResponse النهائي للعميل.

Execution: Task<CheckoutResponse> ExecuteAsync(CheckoutWorkflowContext context, CancellationToken ct)
Section 08 // Resilience Strategy

Reverse Compensation (Saga-like Pattern)

كيف يتعامل الـ Orchestrator مع الفشل المفاجئ بدون ترك النظام في حالة غير متسقة (Inconsistent State).

Business-level Compensation vs. Database Rollback

نقطة جوهرية لازم نفرق بينها كـ Software Architects: ده مش Database Transaction Rollback، دي Business-level Compensation.

في الـ Distributed Workflows أو الـ Multi-step Operations، إحنا منقدرش نفتح SQL Transaction ونعلقها عبر شبكة الـ Payment Gateway أو الـ Shipping Carrier (لأن ده بيعمل Connection Pool Starvation و Deadlocks). لذلك، كل عملية بتتسجل في الـ Database أول بأول، وإذا حصل Failure في خطوة تالية، الـ Orchestrator بيقوم بتنفيذ Compensating Actions عكسية بالترتيب التنازلي للخطوات التي تمت بنجاح.

⚡ Scenario: فشل الشحن بعد نجاح حجز المخزن وخصم الدفع

1. Validation ✓ → 2. Inventory Reserved ✓ → 3. Payment Charged ✓ → 4. Shipment Failed ✗
🔄 Automated Reverse Compensation Pipeline Triggered:
[Compensation Step 1] PaymentProcessingStep.CompensateAsync() ➔ Order.Payment.Status = Refunded
[Compensation Step 2] InventoryReservationStep.CompensateAsync() ➔ product.ReleaseStock(quantity)
[Compensation Step 3] Order.Status = Failed & CancellationReason = "Address rejected" ➔ SaveChangesAsync()

Section 10 // State Container

CheckoutWorkflowContext: Shared Runtime State

لماذا تم إدخال الـ Context وكيف يقضي على الـ Temporal State Pollution بين الـ Steps.

الـ CheckoutWorkflowContext بيوفر Strongly Typed Runtime State بيتنقل بين الـ Steps في الـ Pipeline بدل ما كل Step تعتمد على Variables مبعثرة أو Scope غير آمن.

CheckoutWorkflowContext.cs C# 13 / .NET 9 
public class CheckoutWorkflowContext
{
    public CheckoutCommand Command { get; }
    public Guid OrderId => Command.OrderId;
    public PaymentMethod PaymentMethod => Command.PaymentMethod;
    public string? CardNumber => Command.CardNumber;
    public string ShippingAddress => Command.ShippingAddress;
    public string Carrier => Command.Carrier;

    public Order Order { get; set; } = null!;
    public ReserveInventoryResponse? InventoryReservation { get; set; }
    public ProcessPaymentResponse? PaymentResult { get; set; }
    public CreateShipmentResponse? ShipmentResult { get; set; }
    public CheckoutResponse? Result { get; set; }

    public bool IsInventoryReserved => InventoryReservation != null && InventoryReservation.Success;
    public bool IsPaymentProcessed => PaymentResult != null && PaymentResult.Status == PaymentStatus.Paid;
    public bool IsShipmentCreated => ShipmentResult != null && ShipmentResult.Status == ShipmentStatus.Created;
}
Section 11 // Handler Simplification

Thin Command Handler: Single Responsibility

مقارنة حجم الكود ومسؤوليته بعد تحويله لمفوض بسيط (Thin Delegator).

Approx. 92% Reduction in Handler Size

من 180+ سطر معقد إلى ~15 سطر فائق الوضوح (180 → 15 lines).
Single Responsibility Pattern

الـ CheckoutCommandHandler دلوقتي مبقاش بيعرف أي تفاصيل داخلية عن المخزن أو الدفع أو الشحن. مسؤوليته الوحيدة أصبحت استلام الـ Command وتمريره للـ ICheckoutOrchestrator.

CheckoutCommandHandler.cs (AFTER MIGRATION) ~15 Lines of Clean Code 
public class CheckoutCommandHandler : IRequestHandler<CheckoutCommand, CheckoutResponse>
{
    private readonly ICheckoutOrchestrator _orchestrator;

    public CheckoutCommandHandler(ICheckoutOrchestrator orchestrator)
    {
        _orchestrator = orchestrator;
    }

    public Task<CheckoutResponse> Handle(CheckoutCommand request, CancellationToken cancellationToken)
    {
        return _orchestrator.CheckoutAsync(request, cancellationToken);
    }
}

Section 16 // Value Assessment

Engineering Impact & Architectural Value

تقييم هندسي دقيق للمكاسب المعمارية الناتجة عن الـ Migration.

Separation of Concerns (SoC)

فصل تام بين استقبال الـ Command، وتنسيق الـ Workflow، وتنفيذ خطوات الـ Domains المختلفة.

Maintainability & Velocity

سهولة قراءة وتعديل أي Step في الـ Workflow بدون الخوف من كسر باقي الخطوات أو الـ Compensation.

Deterministic Failure Recovery

سلوك تعويض وفشل واضح وموثوق (Deterministic Reverse Compensation) بدلاً من معالجات الـ Rollback المرتجلة.

High Test Isolation

إمكانية اختبار سيناريوهات الفشل المعقدة عبر Pure Unit Tests بسرعة فائقة وبدون الحاجة لـ Databases.

تنويه معماري مهم: هذه الـ Migration هي تحسين في الـ Architecture, Maintainability, and Testability، وليست بالضرورة تسريعًا في الـ Runtime Performance، لأن الـ Operations الفيزيائية (Database Queries, Network I/O) لم تتغير.

ADR-001 // ACCEPTED

Decision: Adopt the Orchestrator Pattern for Multi-Step Checkout Workflows

Context & Drivers

تضخم مسؤوليات الـ Command Handler في العمليات المتتابعة عبر الـ Domains، وصعوبة معالجة الفشل اليدوي وإجراء الـ Unit Testing.
